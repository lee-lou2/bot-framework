# Security

English | [한국어](ko/security.md)

Models execute without external network access or service credentials. Every model-provider call and tool invocation passes through the broker.

## Trust Zones

| Trust zone | Access boundary |
|---|---|
| Model sandbox (`Apple container` VM) | No external network or service credentials. Connects to the model proxy and MCP relay through a per-run session pinned to its wire protocol (`Anthropic`, `OpenAiResponses`, or `Gemini`). Mounts read-only inputs (`/bot`) and a per-attempt workspace (`/work`). Session tokens pass via environment variables only and are never written to host disk (`agy-cli` expands its template into RAM-only `/tmp/mcp_config.json` inside the VM after dropping privileges). Built-in file reads (`Read`, `/bot`-confined) are available only on `claude-cli`; `codex-cli` and `agy-cli` reject all file built-ins. |
| Direct model API (`worker`) | `anthropic-api` and `openai-api` aliases call upstream APIs directly from the worker with no VM or relay. Models never touch the host filesystem or shell (messages in, text/tool calls out), and tools still route solely through `Broker::call`. Service keys are read just-in-time into request headers only, the active revision is checked immediately before each `POST`, and any response containing that request's key is discarded and closed. Destinations are restricted to the configured `https` `endpoint` (`http` only for loopback IP literals) with redirects and retries disabled ([Architecture](architecture.md)). |
| Operator tool servers (`srt`) | Reviewed, pinned MCP servers run in a separate sandbox outside the model. The broker injects only `secrets` declared for that tool. Servers call external APIs directly through an egress proxy restricted to declared hosts. |
| Trusted host | Gateway, scheduler, worker, broker, store, and Admin UI own authentication, execution, and state. One `SecretStore` resolves logical names: the gateway receives its own adapter credentials directly, and the broker receives per-tool credentials. |

## Model VM Boundary

- **Network boundary.** Apple container's `--internal` (`hostOnly`) network blocks internet egress, but sibling VMs and other open ports on the host gateway remain reachable without VM-side filtering. Session tokens authenticate requests reaching the broker.
- **Trusted init (`bot-init`).** The digest-pinned image starts `/usr/local/bin/bot-init` (POSIX `sh`) as root, re-validates the host-checked numeric IPv4 address and port, applies `nftables` rules allowing only relay TCP and established replies (default drop for everything else, including IPv6), reads back and verifies the rules, and uses `setpriv` to drop to UID:GID `10001:10001` with no supplementary groups, zero Linux capabilities, and `no_new_privs` before executing the pinned CLI (`claude`, `codex`, or `agy`). Any init failure exits with `vm_init_failed` without starting the model.
- **Verification.** Verified on Apple container Linux 6.18.15 (`aarch64`) with Claude Code 2.1.331: the model communicated with a fake upstream through the relay while other gateway ports, peer VMs, and external addresses were blocked, and dropping any of the four init capabilities exited `vm_init_failed` before model launch. Re-run verification whenever changing the image or kernel ([Model VM image](model-image.md)). v2.0 model images require `nftables`; unverifiable rules or privilege drops abort execution.
- **Filesystem & CLI surface.** Rootfs and `/bot` are read-only; the host prepares a per-attempt `/work` so the non-root model writes session logs that the host reads for recovery. Telemetry, auto-updates, and built-in tools are disabled by default (the pinned Claude version permits only agent-requested `Read`). Only per-attempt inputs and `/work` are mounted from the host.
- **Anchor VM.** The worker attaches a credential-free, mount-free anchor VM to the dedicated network, verifies its `hostOnly` property and gateway IP, and binds the relay strictly to that IP (rejecting wildcard, loopback, or other addresses). Failure to verify the anchor or IP aborts model execution. On shutdown, the worker closes its relay before removing the anchor.

## Tool Sandbox, Egress, and Secrets

- **Local tool sandbox (`srt`).** Operator MCP tools run under `@anthropic-ai/sandbox-runtime` (`srt`) `0.0.83`. `deny_read` blocks home, SSH, keychain, and other profile paths; only tool-declared `secrets`, plain config, and host-managed proxy/callback addresses are injected. Real tool processes verify isolation on local macOS and Linux CI; missing `srt`, version mismatch, or failed isolation rejects execution. Shared `/tmp/claude` is blocked from reads and writes (`srt` config on macOS; on Linux, where `srt` re-mounts it, a `bwrap` wrapper overlays an empty read-only `tmpfs` per call without modifying the host directory). Each call runs in a dedicated working directory.
- **Egress & private mappings.** Tools have no direct internet, DNS, or local-network bypass. The egress proxy enforces exact `host:port` per request, on resolved IP addresses, and across redirects. Local tools may reach private endpoints through `host.json` `private_egress` per-profile `host:port -> IP:port` mappings only for hosts and ports already allowed by tool `egress` ∩ profile ceiling. Hiding credential values does not remove the permissions those credentials hold; constrain scopes, egress, and approvals per tool.
- **SecretStore & backends.** On macOS production hosts, use `BOT_SECRETS=keychain` (omitting falls back to dev `env`). With SOPS/age, protect the decryption private key separately from the encrypted file. For short-lived database credentials, add an external OpenBao (MPL-2.0) adapter; Vault is not recommended by default due to BUSL-1.1 ([SOPS](https://getsops.io/docs/) · [OpenBao DB secrets](https://openbao.org/docs/secrets/databases/) · [OpenBao license](https://github.com/openbao/openbao/blob/main/LICENSE) · [Vault license](https://github.com/hashicorp/vault/blob/main/LICENSE)).
- **Profile scoping.** `SecretStore` takes a host-verified `profile` and separator-free `name` separately and reads only `bot/<profile>/<name>` — callers cannot pass a profile or full key, and there is no global fallback. The gateway resolves credentials under the binding's profile; model providers come only from the operator's per-profile allowlist.
- **Single-operator trust boundary.** One operator manages each host: profile files are trusted configuration, and tool credential assignment within a profile is operator-defined. Models never access profile files or the host shell, and memory writes go only to PostgreSQL. Live skill/MCP edits (`skill.*`, `mcp.*`) pass through a single broker gate (`crates/bot-broker/src/service/manage.rs`) that checks `super_admins` and scopes against both the pinned and current revisions (blocking others with `not_super_admin`). SOPS files (`BOT_SECRETS=sops:<file>`) stay in tool sandbox `deny_read`, and secrets saved via `mcp.add` are immediately added to the redaction list and stored encrypted in SOPS/keychain only (raw `secret_value` and `secret_values` are masked on approval cards too). Multi-operator hosts are out of scope for v2.0.
- **Untrusted recalled memory.** The worker tags provenance on member-editable recalled memories and injects their body only as untrusted reference material in user input.

## Walkthrough — Deleting a Calendar Event

1. **Gateway auth.** CLI checks the local OS user; Slack checks the authenticated Socket Mode session plus app and team IDs; HTTP checks registered issuer, audience, and expiry. Host config maps the member and reply conversation, rejects unregistered callers, and enforces per-entrance rate limits.
2. **Broker authorization.** Every tool call computes **requester permissions ∩ agent ceiling ∩ tool scopes** (further capped by parent delegation scope and profile policy) and enforces per-principal rate and concurrency limits. Static `cron` evaluates as the profile's service principal; chat-created schedules and follow-ups retain their creator's identity and permission ceiling.
3. **Risk & approval binding.** `read` queries, `write` mutates, and `irreversible` cannot be undone. `irreversible` calls and policy-selected `write` calls require human approval bound to: run, generation, call ID, profile, requester, approver, risk class, policy revision, tool revision, SHA-256 of canonical JSON (RFC 8785) over full validated `args`, expiry, and one-time nonce. The approval card renders target and mutation from the same broker-validated arguments.
4. **Human verification & commit.** Slack buttons verify the authenticated Socket Mode session (app, team, clicking user); Admin API verifies operator auth and CSRF token. The clicker must match the pre-designated approver (default: requester; static service schedule: profile-designated human; explicit-destination schedule creation/delivery: schedule owner). Models and service principals can never approve. Approval consumption, call start, and audit commit atomically, after re-checking current policy immediately before execution. Revocation, rejection, or expiry blocks execution; risk escalation, rule changes, generation bumps, or arg changes invalidate prior approval and require a fresh card. Model IPC and tool channels bind to run and generation on every message.

## Guarantees and Boundaries

- **Model proxy filtering.** Forwards only declared request fields and client tools; rejects provider-side web search, code execution, remote MCP servers, and container calls. Streaming inspection checks events and decoded chunks: if a chunk tail matches ≥3 bytes of a known key prefix, it holds that suffix until the next chunk and discards it if a full key forms. Open streams terminate on session-token revocation and periodic claim checks.
- **Policy enforcement boundary.** Skill docs, model outputs, and events never grant permissions; enforcement occurs at the broker tool-call boundary. Operator tools are trusted code within their declared credentials and hosts — ensuring a `read` tool only reads depends on install review and read-only credentials. Each approval fixes exact targets and quantities in `args`; targeting anything else requires a separate approved call.
- **Outbound `destination` rules.** Mutating tools that transmit declare `destination: reply` (pinned to the authenticated origin conversation/thread) or `destination: {recipient: args.to, content: args.message}`; non-transmitting mutating tools omit it. Replying in-thread uses existing post permissions. Sending to any other channel, person, email, webhook, or external account escalates to `irreversible` even for host-allowed services; the broker displays and pins exact recipient, content, and attachments on the approval card and blocks sending if either cannot be resolved.
- **Private-memory taint.** Reading any `private` memory persists a run flag before data reaches the model. From then on, `external` tools (including `read` searches) require human approval bound to exact outbound arguments on every call. The flag survives resume and delegation, merges back from child results to parents, and is shared across concurrent runs in the same request tree. Finer-grained data classification is out of scope for v2.0.
- **Output & secret checks.** Secret values never enter the model sandbox, and trusted tools must not return credentials. The broker validates result size, shape, and exposure before returning to the model (covert exfiltration by malicious operator code cannot be detected). Tool outputs and effect receipts are checked only against credentials used by *that call* and token shapes — never against the cross-profile historical redaction list used for observability/admin responses, so one profile cannot probe secrets registered in another. Replies and attachments re-check origin destination and current post permissions before sending. Memory is partitioned by profile, agent, and owner.
- **Remote (Streamable HTTP) MCP servers.** Because the broker connects directly outside `srt`, equivalent controls are enforced separately:
  - Target must be one configured `host:port` strictly inside tool `egress` ∩ profile ceiling; every connection resolves and inspects all IPs, rejecting if any is private.
  - Plain `http` is allowed only for loopback IPv4 literals (canonical form for numeric-ending hosts); redirects are never followed.
  - Active revision is re-checked before every request so stale processes cannot hit revoked endpoints.
  - Bearer tokens are read by name into the Authorization header only; any response containing the token is discarded.
  - Write calls accept only `2xx` responses with matching request ID (anything else is held as unknown outcome); connection close never proves remote termination; `effects: true` is unsupported (no remote callback channel).
  - Tool definitions (name, description, input schema) must match the approved `tools.lock.yaml` hash before calling; `tools/list` is untrusted, so `bot mcp sync` checks credential exposure and schema and writes the lockfile only after receiving all pages.
- **Private memory sharing & writes.** `memory.share`, `memory.save`, and `memory.forget` are allowed only for the authenticated human owner in their own DM or CLI. `memory.share` reads that single ID and renders the full scope and body to the owner (refusing to proceed if the full body cannot fit on the card); `memory.save` enforces a 500 active-entry quota, exact/near-duplicate deduplication, non-destructive `supersedes`, and approval escalation whenever `private_memory_read` is set (never sending unapproved text to an external embedding endpoint). Bodies are omitted from approval lists, run details, and audits visible to others. When `host.json` configures `embeddings`, embedding requests follow the same `https`/loopback-only endpoint validation, double active-revision check, profile-scoped `SecretStore` resolution, and response leak scanning as direct model APIs.
- **Audit chain.** One host-wide hash chain commits sequence number, previous hash, principal, target, input digest, and verdict in the same transaction as every state change. Operators verify tamper-evidence by recomputing the full chain (does not defend against a DB superuser who can rewrite the entire database). Logs and errors emit allowlisted metadata only.
- **Observability & sensitive DMs.** OTLP traces record metadata only by default; capturing prompts and tool results is external data egress requiring explicit per-profile opt-in, secret redaction, and a profile-specified collector (omitted if unset or unavailable). Trace, log (`admin.logs`), and issue (`admin.issues`) endpoints accept `https://` directly (Langfuse, LangSmith, remote OTLP, Sentry, etc.); plain `http://` is accepted without opt-in only for loopback/private addresses (other plaintext URLs require `remote: true` in that section to start). Host-level observability credentials reference SecretStore names (`bot/host/<name>` default or named profile) rather than literal values in `host.json`, and log/issue bodies and tags pass through the live `Redactor` before export. Approval nonces and sensitive-DM raw payloads are excluded from content capture and issue tags. Sensitive DMs default to private handling; if the matched trigger sets `private_pass: true` and its tool returns a valid empty PASS, original body and attachment references move to a normal run (normal conversation policy then governs model input and traces; the private ledger and intake audit never store raw payloads) ([Admin and observability](admin.md)).
- **Pre-approved static cron (`preapproved`) & `human_approval`.** A `preapproved` static cron binds its approval ID to the fingerprint of profile, trigger, source, principal, scopes, tool, install revision, fixed args, allowed `(operation, target)` pairs, cap, and target mapping. On both call-start commit and every new external write grant, under the same PG lock, the broker re-verifies active set, approval ID, pause generation, allowed pair, and daily UTC cap while recording usage and audit atomically. Grants apply solely to direct calls of that admitted occurrence — never inherited by models, delegations, wakes, other triggers, or event bodies. The broker guarantees authorization and count of declared `(operation, target)` pairs; actual recipient binding relies on target-scoped credentials or reviewed pinned adapters. **Limitation:** changing destinations requires a new credential name and fresh approval; rotating the secret value under the same name is not detected (only operators with SecretStore write access can do so). A designated human's message or reaction (`human_approval`) substitutes once for one approval step only when the entrance-authenticated actor of that event is the approver under both current and pinned revisions, and never bypasses independent requirements (post-private-recall confirmation, private, owner-only).
- **Future hardening options.** Per-role OS UIDs and DB accounts, distributed mTLS, externally signed checkpoints, step-up re-authentication for high-risk approvals, and broker-hosted connectors with an operation catalog.
