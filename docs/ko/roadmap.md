# 로드맵 및 공개 인수 기준

[English](../roadmap.md) | 한국어

로컬 데모와 모든 런타임 역할에 대한 인수 게이트입니다. PostgreSQL 테스트는 `BOT_TEST_DATABASE_URL`에서 전용 테스트 데이터베이스 URL을 읽습니다. ([릴리스 체크리스트](release.md))

| 단계 | 담당 크레이트 | 인수 기준 |
|---|---|---|
| 1. 프로필 | `bot-profile`, `bot-core` | 공개 체크아웃에서 독립 빌드. 동일 바이너리에 두 번째 프로필과 손자 에이전트 추가. 깨진 링크, 중복 바인딩, 누락된 서버를 활성화 전에 거부. |
| 2. 큐 및 스케줄 | `bot-store`, `bot-runtime` | 워커 2개·스케줄러 2개 환경에서 멱등 요청/크론 접수, 리스 인계, DST 및 장애 복구(catch-up), 데드레터 재개, 중복 없는 부모 깨우기 검증. |
| 3. 도구 | `bot-broker` | 모델은 시크릿 0개·네트워크 차단 상태이며, 도구는 선언된 시크릿과 이그레스 호스트만 받음. 형제 시크릿 유출, 프록시 우회, 타 주체 승인, 인자 변조, 재전송(replay), 회수된 스코프 거부. |
| 4. 인그레스 및 응답 | `bot-gateway`, `bot-runtime`, `bot-cli` | CLI, Slack, HTTP 전반의 검증된 접수와 원래 대화 응답. 미등록 사용자와 레이트 리밋 초과 거부. 위임과 메모리에서 프로필/소유자 경계 강제. |
| 5. 운영 | `bot-broker`, `bot-store`, `bot-admin` | 단일 단계 삭제와 다단계 도구를 전송 전·후에 중단해 원본 영수증 또는 `held` 확인, 자동 중복 전송 0건 보장. Admin UI 보류(hold), 감사 체인, OTLP 장애 허용, 백업 복원 검증. |
| 6. 공개 데모 | `bot-cli` | 깨끗한 호스트에서 README 로컬 데모 재현: CLI 대화, 직접 크론 호출(모델 호출 0회), 자가 승인 단일 삭제가 `--role all`과 역할 분리 모드에서 동일하게 동작. |

## 보안 및 복구 인수 매트릭스

| 시나리오 | 필수 결과 |
|---|---|
| 두 프로필에 이름은 같고 값이 다른 합성 시크릿 존재 | 각 도구는 자기 프로필 값만 받고 교차 네임스페이스 경로를 거부함. 운영자 이그레스 상한 밖의 연결과 미허용 모델 프로바이더를 차단함. |
| 같은 서비스에서 다른 수신자에게 메시지 발송 | 수신자와 본문을 표시하는 별도 승인 전에는 발송 0건. 승인 후 본문·첨부·수신자가 바뀌면 발송 0건. |
| 승인 대기 중 위험도 상승 또는 워커 세대 변경 | 이전 버튼/채널 거부; 새 승인은 최대 1회만 소비. |
| 중복 이벤트, 프라이빗 DM, 반복 HTTP 조회 | 유효한 인자를 가진 가장 이른 도구만 실행. 프라이빗 DM은 기본적으로 비공개 유지; 선택된 `private_pass: true` 트리거의 유효한 빈 PASS만 원래 질문과 첨부 참조를 담은 정규 실행 1건을 생성. HTTP는 일관된 동기 상태/본문 또는 `202` 이후 동일한 결과를 반환. |
| 외부 쓰기 직전 워커 크래시 | 이전 도구가 종료되고 미실행이 확인될 때까지 재실행 0건; 확인 후 같은 `_meta` 호출 ID로 재개. |
| 단계 확인 후 최종 호출 응답 유실 | 보류(hold) 큐가 커밋된 단계 영수증을 보존하고 호출 수준 영수증으로만 재개; 전체 호출 `not_executed`는 거부되며, 취소 시 열린 도구 보류가 닫힘. |
| 위임과 취소의 경합 또는 지연 완료 | 취소는 이미 커밋된 자식까지 포괄하며 지연 위임을 거부. 취소가 먼저 커밋되면 지연 완료는 응답 0건을 내고 부모를 한 번만 깨움. |
| 일시적 오류와 리스 만료로 재시도 예산 소진 | `dead` 행에 최종 시도 횟수 기록; 운영자 재개 시 시도 횟수 0부터 다시 시작. |
| PG 재시도 한도 1; 종료 인계가 활성 세트 교체 락에서 타임아웃 | 교체 커밋 후 새 워커가 만료된 리스를 선점해 시도 0에서 성공. 같은 세트에서 다시 만료되거나 세트 메타데이터가 없으면 시도 1회 소비. |
| 만료된 `beat` vs 신규 유입 이벤트 | 만료된 beat가 직렬화 키 소유권을 유지. 도래한 재시도, 만료된 리스, 새 실행은 잠긴 행을 건너뛰며 준비 시각 순으로 선점. |
| 선점된 실행의 손상된 대상(target) | 원본 페이로드와 고정 사유를 기록해 해당 실행만 격리; 무관한 실행과 대기 중인 부모는 계속 진행. DB 오류 시 선점을 롤백. |
| 체크포인트 상한 및 완료 충돌 | 1 MiB 저장소 상한을 넘는 계획/결과와 반복 완료 충돌은 1회 시도에서 종료; 일시적 저장소 오류는 저장된 계획/영수증에서 재개. |
| 같은 활성 세트의 워커에 `SIGTERM` 전달(재시도 한도 1) | 8초 유예 후 종료하고 세션을 폐기해 실행을 시도 0의 `ready`로 되돌림; 다른 워커가 완료. 구버전 선점의 쓰기는 새 소유자를 덮어쓰지 못함. |
| 반복 스케줄 발화 전에 응답 경로 회수 | PG가 사유별 감사 코드를 기록; 이중 스케줄러 경합/재시도 환경에서도 `unrouted`만 원래 채팅에 고정 안내 1건을 게시. |
| 단계 영수증 사전 조회 중 도구 중단 | 같은 호출의 재조회는 단계·보류·감사 0건으로 `none` 반환. 기존 단계에 다른 인자를 넘기면 `conflict`, 확인된 단계는 원본 영수증 반환. |
| 관리자가 보류 단계를 `not_executed`로 해소하고 워커 재개 | 조회 결과는 `held`, `resolution:"not_executed"`, `send:false`. 해당 단계의 첫 재선점만 `send:true`를 받아 해소를 소비. 같은 세대의 구버전 선점은 `stale`, 미등록 호출은 `denied`, 누락 단계는 `none`, 타 프로필 ID는 격리. |
| 운영자가 PG 실행 상세에서 재개/취소 실행 | 루트 일반 실행만 허용. 응답이 유실된 명령을 재시도해도 상태 전이와 감사는 1회만 수행. 이전 선점은 새 선점을 취소 불가. 취소는 하위 트리로 전파되며, 미해소 보류가 있으면 보류 화면으로 안내. |
| 에이전트별 내장 도구 게이팅 | 생략·빈 값·미선언 자식은 내장 도구 0개; 명시된 역할만 `read` 허용. 셸·쓰기·웹 선언은 활성화 전에 실패. |
| 실제 Claude CLI + 목 모델 스트리밍 -> MCP 도구 -> 모델 왕복 | 도구 실행 정확히 1회; 프로바이더 키와 세션 토큰이 각 경계 안에 머무름. 모델 VM의 네트워크/FS 격리는 별도 호스트 테스트에서 검증. |
| 실제 Claude CLI + 목 업스트림 + 쓰기 승인 중 PG 워커 교체 | 새 `HOME`에서 같은 세션 재개: 승인 소비 1회, 도구 실행 1회, 영수증 1건; 후속 모델 턴은 원래 tool-use ID와 실제 결과를 유지. |
| 동일 구성에서 부모가 MCP로 직계 자식에게 위임 | 단일 워커가 자식을 완료; 부모를 재시작해도 자식 실행 1건과 도구 실행 1회만 남고 자식 결과가 원래 위임으로 전달. |
| 같은 도구·인자 2회 계획 + 중복 요청 전달 | 서로 다른 위치가 각각 1회 실행되며, 같은 위치의 재전달은 캐시된 결과를 반환. |
| 보류 결정 응답 유실 후 동일 응답/도구/단계가 다시 보류됨 | 첫 번째 발생 ID 재시도는 감사 1건과 함께 캐시된 성공을 반환; 새 발생은 별도 결정 전까지 열린 상태 유지. |
| 본인 DM/CLI, 타 사용자, 채널, 위임 자식 간 메모리 검색 | 본인 DM/CLI만 `private` 항목 조회 가능; 채널은 부모·자식 모델 프롬프트나 응답으로 비공개 메모리를 절대 유출하지 않음. |
| `private` 메모리 조회 후 검색 도구 호출 | 재시작이나 위임을 거쳐도 아웃바운드 인자 승인 전에는 외부 요청 0건. |
| 프라이빗 DM 접수 및 재전달 | 지정된 도구만 1회 실행; 기본 프라이빗 모드는 원문 입출력을 원장·모델·트레이스에서 제외. 유효한 빈 PASS(`private_pass: true`)와 정규 접수 사이 크래시 시 같은 리비전·트리거·시크릿으로 `:pass` 아래 1회 재전달. 시작 전 실패는 동일 입력으로 재선점; 불확실·만료 호출은 재전달 없이 보류. |
| 타 사용자가 메모리 소유자 설정/수정/삭제 시도 | `owner`는 인증된 주체에 고정 유지; 타 사용자 항목 변경 0건. |
| 메모리를 `profile` 스코프로 공유 | 소유자만 전체 내용 조회 가능; 카드 생성 후 수정하면 미소비·미공유 유지; 응답 유실 후 재시도해도 공유 감사는 1건만 기록. |

공개 CI는 `rustfmt`, Clippy, 테스트, 스키마/예제 검증, 파일 600줄 제한(생성된 `Cargo.lock` 제외), 허용 라이선스(`MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `Unicode-3.0`, `Zlib`, `BSL-1.0`), 시크릿 스캔(릴리스 전 Git 히스토리 포함)을 강제합니다. 실제 프로필과 비공개 식별자 사전은 로컬 릴리스 점검에서만 실행하며, 운영 전환 시에는 드라이런과 롤백 리허설까지 통과해야 합니다.

## 추가 릴리스 전 검증

- 재시도 한도 1에서 깔끔하게 종료되는 CLI 명시적 대상 거부는 `claude_attempts`로 추적하며, 위임 인자 오류를 같은 마커에 기록하는 작업은 열려 있습니다. 재배포 시 고정 리비전 복원과 손상된 스케줄의 격리 종료는 실제 PostgreSQL에서 검증합니다. ([신뢰성](reliability.md))
- **대화형 스케줄:** 두 스케줄러가 처리하는 1회성·반복 CLI 스케줄에서 재전달당 생성 1회, 도래 틱당 실행 1회, 취소-접수 경합, DST, 구성원 권한 회수, 타 사용자 조회/취소 거부, 명시적 `<quiet>` 완료를 검증합니다.
- **Slack 명시적 대상 스케줄:** 같은 프로필의 등록 채널을 대상으로 하는 `schedule.create`는 스케줄 생성 시 소유자 승인 1회, 매 발화마다 아웃박스 응답 1건을 내기 전 2차 승인 1회가 필요합니다(각 승인 전 행 0건). 채널을 제거하면 이후 발화/전달이 중단되며, CLI/HTTP 입구는 명시적 대상을 거부합니다.
- **일반 DM 인그레스 꺼짐 시 소유자 DM 승인 카드:** 공개 채널에서 스케줄을 생성하면 두 카드 각각을 소유자 DM에 1회 열고 원래 채널에 상태 줄 1건(posted / failed / uncertain)을 게시합니다. 타 사용자/DM 클릭이나 DM 영수증 누락 시 소비 0건·전달 0건이며, 재전달에도 카드·안내·발송이 중복되지 않습니다. ([신뢰성](reliability.md))
- **도구 후속 확인:** 결과 저장 직전·직후에 중단해도 원장 영수증과 1회성 스케줄 1건이 보존되고 체인 상한에서 멈춥니다.
- **도구 설정 우선순위:** 실제 도구에서 부모 설정, 자식 재정의, 형제 격리를 검증하고, 시크릿 환경 변수 충돌과 필수 키 누락을 실행 전에 거부합니다.
- **영구 도구 파일:** 해당 기능이 필요한 프로필을 마이그레이션하기 전에 옵트인 어댑터 뒤에서 검증합니다(재시작 간 소유자 전용 읽기, 서버/모델 간 차단, 심볼릭 링크 탈출 방지, 동시 쓰기, 하드 쿼터).

## v2.0 이후 모델 설정

- `providers.<alias>`는 `claude-cli`(기본값 `medium`, 최대 출력 토큰 8,192), `anthropic-api`, `openai-api` 전반에서 `effort`를 지원하며, `max_tokens`(`openai-api`에서는 `max_completion_tokens` 포함)를 지원합니다. 향후 호스트 상한 내에서 에이전트별 `effort` 및 출력 토큰 재정의를 추가할 예정입니다.
- Pi CLI(`kind: "pi"`)는 v2.0에서 미지원입니다. 미사용 러너 코드는 제거되었고(Git 히스토리에 보존), 격리·재개·세션 토큰 경계가 검증될 때까지 호스트 설정에서 `kind: "pi"`는 계속 거부됩니다.

## 시간 라이브러리 마이그레이션

다음 유지보수 릴리스 전에 크론 반복과 과거 보정(catch-up)을 `jiff`로 이전하고, SQLx의 `chrono` 피처를 제거해 SQLx의 `time` 타입으로 전환한 뒤, DST 공백·반복 현지 시각·30분 오프셋·저장된 UTC 커서 재개·이중 스케줄러 스케줄을 현재 구현과 대조 검증합니다. `chrono`와 `chrono-tz`가 의존성 트리에서 제거되면 두 유지보수 예외를 삭제하고 `cargo-deny` 4종 점검을 다시 실행합니다. ([RUSTSEC-2026-0543](https://rustsec.org/advisories/RUSTSEC-2026-0543.html) · [RUSTSEC-2026-0555](https://rustsec.org/advisories/RUSTSEC-2026-0555.html))

## 보류된 결정

임시방편으로 부분 구현이 섞이지 않도록, 현재 범위에서 의도적으로 제외하고 재검토 트리거를 명시한 항목들입니다.

| 결정 | 보류 이유 | 재검토 트리거 |
|---|---|---|
| DB 시계 기준 승인 만료 | 브로커(`crates/bot-broker/src/service/gate.rs`, `crates/bot-broker/src/service/decide.rs`)는 로컬 시계로 만료를 검사하고 스토어는 DB 시계를 강제합니다. 통일하려면 `OpenApproval`, `CallLedger`, 카드, 테스트 대역을 모두 변경해야 합니다. 현재는 호스트 간 NTP 동기화를 전제합니다. | 멀티 호스트 브로커에서 시계 오차로 인한 만료 이상이 발생하거나 `CallLedger::open_approval`을 변경할 때. |
| 배치 단위 승인 만료 정리 | `crates/bot-store/src/queue.rs`는 선점 전 만료된 모든 승인을 일괄 정리하고 실행별 `FOR UPDATE`(`crates/bot-store/src/approvals.rs`)에서 대기합니다. `SKIP LOCKED` 기반 제한 배치에는 재방문 주기와 부분 인덱스 튜닝이 필요합니다. | DB 프로파일링에서 대량 만료나 락 경합으로 인한 선점 지연이 관측될 때. |
| 빈 닫힌 크론 구간 소진 | `until_ms` 이전 발화가 없는 닫힌 창은 `until_ms > cursor_ms` 상태로 남아 오래된 번들을 고정합니다(`crates/bot-store/src/schedule.rs`, `crates/bot-store/src/profile_bundles.rs`). 커서를 섣불리 전진시키면 영구 누락 위험이 있어 `ScheduleStore` 확장과 경계 테스트가 필요합니다. | 수정된 스케줄의 미회수 구버전 번들이 운영 문제가 되거나 `ScheduleStore`를 확장할 때. |
| 크론 DST 현지 시각 "1회 실행" 정책 | 5필드 크론 표현식만으로는 매분 작업과 1일 1회 리포트를 구분할 수 없고, `crates/bot-runtime/src/cron.rs` 기본값을 바꾸면 기존 커서가 깨집니다. 옵트인 필드, 구간 의미론, 승인 봉인, 마이그레이션이 필요합니다. | 일일 리포트의 연 2회 DST 건너뜀/중복을 방지해야 한다는 명시적 요구가 생길 때. |
| 명시적 스케줄 대상의 transport 컬럼 | 일반 응답과 아웃박스는 `reply_transport`/`transport`를 저장하지만, 명시적 스케줄 대상은 Slack 채널 바인딩만 허용하며 `crates/bot-store/src/delivery.rs`에 `slack`이 고정되어 있습니다. 미리 컬럼을 추가하면 봉인과 재검증이 복잡해집니다. | 명시적 스케줄 대상에 두 번째 푸시 전송을 추가할 때(`ScheduleRoutes` + 승인 봉인). |
| 강제 토큰 예산 | 현재는 턴·시간 제한과 출력 토큰 상한으로 제어합니다. 사용량 미보고 업스트림과 CLI 프록시·직접 API 양쪽을 아우르는 스토어 예산기가 없고, 모델별 가격표는 유지 비용이 큽니다. | 가격표 없는 토큰 상한과 미보고 정책으로 깊은 위임 전반의 실행/프로필 토큰 소비를 강제 제한해야 할 때. |
| 모델 호출형 메모리 쓰기(`memory.save`, `memory.forget`) | `MemoryStore::change`를 직접 노출하면 프롬프트 인젝션으로 인한 영구 오염이나 중복 위험이 있습니다. 1:1 전용 스코프, 소유자 승인, 소유자별 쿼터, 멱등성 계약이 선행되어야 합니다. | 완전한 승인·쿼터·멱등성 규칙을 갖춘 대화 중 모델 메모리 쓰기 요구가 확정될 때. |
| `bot eval`(오프라인 프로필 평가) | 프로덕션 바이너리에서 `testing` 테스트 대역을 제외하는 경계(선택적 피처 vs 별도 크레이트)와 맞물립니다. 현재는 `bot validate`와 `bot map --json` diff로 스코프/도구 회귀를 잡습니다. | DB나 외부 API 없이 시나리오별 권한·승인·거부 경로를 검증하려는 반복적 CI 수요가 생길 때. |
| `bot validate --json` | 프로필 검증은 안정된 `Issue.code`를 내지만 호스트 설정 오류는 아직 자유 형식 문자열입니다. 버전이 지정된 JSON 스키마와 호스트 오류 코드 계약이 먼저 필요합니다. | 에디터나 CI 파이프라인에서 기계 판독 가능한 검증 출력이 필요할 때. |
| `host.schema.json` | 호스트 검증은 9개 모듈에 걸친 의미·경로·지문 검사가 대부분이며, `.github/scripts/docs_contract.py`가 이미 문서화된 키를 지킵니다. 지금 스키마 우선 파싱으로 재작성하면 비용 대비 효과가 낮습니다. | 외부 도구에서 `host.json` 자동 완성/스키마 검증을 요구하거나 중복 키 파서를 통합할 때. |
| 포트 적합성(conformance) 테스트킷 | 브로커 테스트 대역이 순환 의존성 제약에 걸립니다. `bot-core` 페이크와 공통 PG 적합성 매크로를 추출하려면 여러 크레이트에 걸친 테스트 재구성이 필요합니다. | 페이크 스토어와 PostgreSQL 간 불일치가 반복되거나 두 번째 영속 백엔드를 추가할 때. |
| Clippy 함수 길이 임계값 | `.github/scripts/check_contracts.py`가 이미 파일 600줄 상한을 강제합니다. `clippy.toml` 길이·복잡도 임계값을 켜려면 기존 함수에 대한 단계적 조임 계획이 필요합니다. | 600줄 파일 안의 과도하게 긴 단일 함수가 반복적인 리뷰 병목이 될 때. |
| Linux용 모델 VM | Linux 호스트는 VM 없는 직접 API(`anthropic-api`, `openai-api`)를 실행할 수 있습니다. Linux `claude-cli` VM 어댑터에는 전용 격리·네트워크 차단·재개 검증이 필요합니다. | 직접 API 대신 Linux에서 로컬 `claude-cli`를 실행해야 할 운영 요구가 확정될 때. |
| 외부 MCP 클라이언트 라이브러리 | 자체 클라이언트(`crates/bot-broker/src/mcp.rs`, `crates/bot-broker/src/mcp/`)는 크기·헤더·스키마 해시 고정 강화 테스트를 통과합니다. 외부 크레이트가 이 보장을 유지하는지 검증된 스파이크가 아직 없습니다. | 새 MCP 전송/인증/버전 추적이 내부 클라이언트 유지 비용을 넘을 때(기존 강화 테스트 통과가 전제). |
| 데이터 보존/정리 정책 | 감사 체인, 열린 보류, 멱등성 키, 참조 중인 리비전을 성급히 삭제하면 중복 실행이나 감사 손상이 발생합니다. 테이블별 경계와 재전달 안전성 증명이 필요합니다. | 완료된 실행·체크포인트·아웃박스 증가가 DB 용량이나 조회 지연에 측정 가능한 영향을 줄 때(미참조 종료 행 드라이런 집계부터 시작). |
| 점진적 스킬 본문 로딩 | 스킬 본문을 지연 로딩하면 읽기 경계, 스캔 한도, 리비전 해싱이 달라집니다. 현재는 `SKILL.md` 프런트매터 `description`을 구조체에 유지하고 에이전트당 64 KiB 상한(`crates/bot-runtime/src/context.rs`) 안에서 본문을 주입하는 방식으로 충분합니다. | 에이전트가 64 KiB 스킬 본문 상한에 자주 도달하고 측정 데이터가 요약 우선 지연 로딩을 정당화할 때. |
