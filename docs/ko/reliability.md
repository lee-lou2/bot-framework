# 신뢰성과 장애 복구

[English](../reliability.md) | 한국어

**접수 완료는 PostgreSQL 커밋을 의미합니다.** 네트워크나 프로세스 장애 이후 실행 시도는 반복될 수 있습니다. 내부 DB 상태는 고유 키와 트랜잭션으로 정확히 한 번만 적용되며, 외부 쓰기는 수신 측이 증명할 수 있는 범위까지만 복구합니다.

## 고유 키와 원자적 경계

| 단위 | 고유 키 및 원자적 트랜잭션 경계 |
|---|---|
| 프로필 활성화 | 예상 활성 세트 리비전이 현재 값과 일치할 때만 새 활성 세트, 메모리 시드, 정적 트리거 구간 전환, 감사를 함께 커밋합니다. 하나라도 실패하면 전체 롤백되며, 동일한 세트로 재시작하면 쓰기 없이 합류합니다. |
| 표준 접수 (CLI, Slack, 웹훅) | `(profile, binding, issuer/principal scope, stable event/request ID)`. 입력 해시는 인증된 대화, 첨부파일, 본문 및 (HTTP의 경우) 실제 메서드와 하위 경로를 포함합니다. 같은 키 + 입력은 기존 실행을 반환하고, 메서드나 경로가 다르면 충돌을 반환합니다. 접수 + 실행 + 대기열 + 감사 커밋 후에만 ACK합니다. |
| OpenAI 호환 접수 | 바인딩과 모델을 아우르는 `(profile, HTTP entrance, authenticated principal, Idempotency-Key)`. 키 예약, 진입점별 진행 중 상한, 실행, 감사가 함께 커밋됩니다. 같은 키 + 입력 + 모델은 슬롯을 소비하지 않고 기존 실행을 반환하며, 입력이나 모델이 다르면 충돌을 반환합니다. |
| 스케줄 | `(profile, agent, trigger ID, scheduled UTC instant)`. 스케줄 편집 시 적용 시각 기준으로 구간을 분할합니다. DB 시계 커서, 발생 회차 행, 대기열이 한 번의 커밋으로 전진하며, 리더 페일오버와 동시 스케줄러도 같은 키로 수렴합니다. |
| 위임 | `(parent run, saved step ID)`. 자식 실행과 부모 대기가 함께 커밋되어 부모 장애 시 같은 자식 결과를 재사용합니다. 모델 단계, 도구 호출, 결과는 재개를 위해 체크포인트됩니다. |
| 응답 | `(run, origin destination, answer seq)`. 완료 결과와 아웃박스가 함께 커밋되며, 전달은 도구 이펙트와 동일한 결과 불명 보류 및 영수증 정책을 따릅니다. |

**크론, DST 및 `beat` 규칙:**
- 크론은 프로필 현지 시간으로 평가합니다. 서머타임(DST)으로 건너뛴 분은 건너뛰고, 반복되는 해제 시점의 분은 서로 다른 UTC 시각으로 두 번 실행됩니다.
- 다운타임 중 놓친 회차는 가장 오래된 것부터 제한된 배치로 따라잡습니다.
- 건너뛰기/병합은 상태 `beat` 트리거에서만 허용되며, 대기 중인 1회분과 실행 도중 도착한 신호를 구분해 최신 갱신이 유실되지 않도록 합니다.

## 워커 인계

### 대기열 순서, `0024` 마이그레이션, 손상된 대상

- 잠기지 않은 일반 실행은 `ready_at`, 재시도 시각 또는 리스 만료 시각 순(이른 순, 동률이면 `created_at` → `run_id`)으로 한 줄에 대기합니다. 승인 해제, 반환, 재개 시 대기 시각을 현재 DB 시각으로 재설정해 먼저 기다린 작업이 앞에 유지되며, 명시적 미래 준비 시각은 그대로 보존됩니다. 하나의 `beat` 키는 리스 만료 전까지 `leased` 선행 실행에 속하며, 만료 후 시도 횟수 제한에 따라 회수되거나 종료됩니다.
- **마이그레이션 `0024` (`crates/bot-store/migrations/0024_queue_order.sql`):** 레거시 `ready` 행의 null `ready_at`을 `created_at`으로 백필하고 `bot_runs_eligible` 인덱스를 생성합니다. 컬럼 기본값 변경은 인덱스 생성과 커밋까지 `bot_runs`에 락을 유지해 읽기/쓰기를 차단하므로, 대규모 DB에서는 운영 규모 복제본에서 벤치마크하고 점검 창을 잡으세요. 모든 레거시 워커가 퇴역한 뒤 별도 마이그레이션으로 `bot_runs_leased`를 삭제하고, 새 인덱스에 대한 관리자 목록 쿼리 플랜을 확인한 뒤에 `bot_runs_ready`를 삭제하세요.
- **읽을 수 없는 대상:** 후보 행의 저장된 대상을 디코딩할 수 없으면 스토어가 원시 페이로드를 보존한 채 `invalid_target`으로 데드레터 처리하고, 대기 중인 부모가 있으면 자식 실패를 기록한 뒤(부모가 잠겨 있으면 해당 자식은 건너뜀) 계속 진행합니다. 한 번의 클레임은 최대 8개 후보를 검사하며(나머지는 다음 클레임 대기), DB 오류는 일시적 실패로 반환합니다. 운영자 재개에는 디코딩 가능한 대상이 필요합니다. 새 대상 형식을 배포할 때는 활성 세트를 교체하거나 레거시 워커를 먼저 비우세요.

### 승인 또는 자식 실행을 대기하는 CLI

1. 런타임은 실행당 하나의 세션 UUID를 할당합니다. 도구 실행 전 호스트가 받은 전체 모델 응답 도구 목록을 CLI 세션 로그와 대조해 해당 턴을 PostgreSQL에 영구 저장합니다(한 턴에 여러 도구를 계획한 경우 모든 슬롯 보존. 첫 MCP 요청이나 단일 세션 줄만으로는 턴 완료를 증명하지 않음).
2. 논리적 호출 식별자는 `(profile, run, saved assistant turn, tool slot)`입니다. 호스트의 `CallBook`이 와이어 `tool_use_id`, 도구 이름, 정규 인자 해시를 해당 슬롯과 대조합니다. 같은 슬롯의 재전달은 같은 호출을 반환하며, 같은 수신자에게 동일한 인자를 보내는 서로 다른 두 슬롯은 별개의 두 호출입니다.
3. 승인 대기나 직접 자식 위임 시 부모는 CLI 연결과 워커 리스를 놓습니다. 자식 결과는 `(parent run, call ID)` 아래 저장되므로 단일 워커로도 자식을 실행할 수 있습니다. 재개하는 워커는 새 클레임 아래 현재 권한을 확인하고 저장된 호출을 이어가거나 기존 자식 결과를 읽습니다.
4. Claude 어댑터는 새 클레임 작업 디렉터리에 세션을 복원하고, 검증된 원장 결과를 도구 사용당 한 번씩 `tool_result`로 연결해 `--resume <UUID>`로 재개합니다. 기존 결과는 원장과 대조 검증하며, CLI 중단 오류를 완료로 채택하지 않고 증명되지 않은 호출-결과 연결은 보류 상태를 유지합니다.

체크포인트에는 복원에 필요한 대화 기록만 보관합니다. 각 클레임은 새 릴레이 토큰, MCP 설정, 작업 디렉터리를 받아 오래된 프로세스가 새 세션 파일을 덮어쓰지 못하게 하며, CLI 세션 형식은 런타임 어댑터가 관리합니다.

- **응답 봉인:** 브로커는 CLI로 마지막 JSON/SSE 이벤트를 보내기 전에 도구가 포함된 완전한 응답을 `cli-resp-<message.id>`에 기록합니다(프로바이더 use ID, 전체 도구 이름, 순서대로의 JSON 인자). 잘린 응답, 누락된 메시지 ID, 중복 use ID는 도구를 시작할 수 없으며, 커밋 후 연결 끊김 재시도는 키와 내용이 일치할 때 기존 기록을 재사용합니다.
- **턴 커밋:** 런타임은 같은 메시지 ID의 CLI 기록을 모아 모든 use ID, 순서, 이름, 인자를 검증하고 세션 기록(`cli-rec-<seq>`), 도구 슬롯(`cli-use-<tool_use_id>`), 턴 그룹(`cli-group-<turn>`, 여기서 `turn`은 첫 어시스턴트 기록 번호)을 단일 트랜잭션으로 기록합니다. 릴레이는 현재 클레임 아래 use ID와 그룹을 읽으며, 처음 본 그룹은 모든 슬롯을 검증합니다(예: MCP `agenda_delete`는 `mcp__relay__agenda_delete`와 정규 JSON 인자가 일치해야 함). 재전달은 동일한 `CallId::cli(turn, slot)`로 해석됩니다(위임도 이 ID 사용).
- **재개 재생:** 원장에 없는 릴레이 도구는 검증된 슬롯에서 현재 권한과 승인을 재확인합니다. 완료된 호출은 저장된 결과를 재사용합니다(MCP `content`와 `isError` 보존, 일반 JSON은 단일 텍스트 블록으로 감싸고, 거부/만료는 고정 오류 단어 사용). 검증 불가능한 VM 내장 도구 결과는 호스트가 임의로 대체하거나 성공 처리하지 않습니다.

### 실행 전 거부 봉인

Claude CLI 프런트와 직접 API 워커 모두 현재 클레임 아래 검증된 계획 슬롯에서 확정된 실행 전 거부를 `cli-refusal-<call_id>`에 봉인하고 재개 시 동일한 단어를 재생합니다. CLI는 `isError: true`, Anthropic API는 `is_error: true`, OpenAI 호환 API는 대응 도구 메시지에 해당 단어를 넣습니다.

- 단계형 API 워커는 도구 호출 전 턴의 전체 계획을 `turn-N`에 기록합니다. 앞선 호출이 거부되고 뒤 호출이 승인을 대기하면, 다음 워커는 브로커를 호출하지 않고 봉인된 거부를 재생한 뒤 승인 슬롯으로 이어가며, 모든 호출이 끝나면 묶은 결과를 `end-N`에 기록합니다. 미완료 턴의 성공 영수증과 기존 자식 결과는 재개 시 현재 권한을 재검증합니다.
- CLI는 슬롯별로 요청을 직렬화하여 동시 재전달로 한 슬롯이 거부와 실행 양쪽으로 끝나지 않게 합니다. 계획 검증, 슬롯 락, 봉인 읽기 대기 중 세션이 철회되면(완료와 경합하는 경우 포함) 실행·위임·봉인을 시작하지 않고 `stale`을 반환합니다. 봉인된 정상 거부는 실행 시도 횟수를 소비하지 않으며, 자격 증명이나 라우트를 수정하면 새 모델 슬롯에서 재평가할 수 있습니다. 슬롯 검증 전 거부(잘못된 도구 이름, 인자 구조, `toolUseId`, 계획 불일치, 미검증 계획)는 봉인 없이 단어만 반환합니다. 이미 시작·보류·완료·거부된 원장 항목은 봉인보다 우선하며, 시작 전 열린 기록은 봉인으로 닫힐 수 있습니다.

| 실행 전 판정 | 모델에 표시되는 봉인 단어 |
|---|---|
| 없는 도구 / 잘못된 입력 | `unknown_tool` / `invalid` |
| 권한·스코프 부족, 도구 자격 증명 누락, 허용되지 않은 스케줄 대상 | `denied` |
| 호출 내용 충돌 | `conflict` |
| Claude CLI 호출의 리비전 불일치 | `stale` |
| 속도 또는 동시성 제한 도달 | `unavailable` |

- 속도/동시성 제한은 해당 호출 자체의 결과와 함께 거부가 확인된 경우에만 봉인합니다(호출별 마커로 이전 거부나 읽지 않은 플래그가 같은 슬롯의 다른 오류로 번지는 것을 방지). 스토어 장애/원장 읽기 불가(`unavailable`)와 클레임 상실 `stale`은 절대 봉인하지 않습니다.
- 브로커가 `Stale`을 반환하면 직접 API 워커는 리스를 확인해 유효하면 새 리비전으로 같은 호출을 재평가하고, 상실했으면 물러납니다.
- 스토어가 없는 스케줄 ID나 잘못된 시간/시간대를 보고하면 단계형 워커는 해당 오류를 모델에 반환합니다. 거부 봉인은 원장과 사전 평가로 확정된 경우에만 기록되며, 스토어 `Unavailable`은 턴을 재시도합니다.
- 원장을 읽지 못하거나 봉인을 쓰지 못하면 슬롯은 미확정 상태로 남습니다. 단계형 워커는 턴을 재시도하고(브로커 판정 감사와 봉인 쓰기는 분리되어 있어 그사이 장애가 나면 재평가 시 감사가 하나 더 추가될 수 있음), CLI는 `unavailable`을 반환하며 종료 시점에도 미확정이면 `session_unsaved`로 재시도합니다(시도 횟수 소비). 리스를 잃은 워커는 `stale`로 물러나며, 이미 시작되었거나 불확실한 호출은 원장 복구를 따릅니다.
- 손상된 봉인은 실행을 차단합니다(라이브 CLI에서는 `unavailable`, CLI 복원과 API 워커에서는 `corrupt_checkpoint`). CLI 프런트의 잘못된 `delegate` 인자는 즉시 `invalid`를 반환하며, CLI 재개에서도 저장된 인자를 동일하게 검증합니다.

### 재배포 및 복원 수용 기준

`--activate` 또는 재시작 시 역할을 열기 전에 새 프로세스는 저장된 프로필 번들에서 이전 리비전을 복원하며 복원에 실패하면 시작을 거부합니다. 실제 PostgreSQL과 다중 OS 프로세스 테스트로 아래 각 사례를 검증하며, 준비-게시 경합(재확인이 `Stale`로 거부하는 동작, 재시도 판정 테스트와 함께 검증)과 두 호스트의 동일 세트 동시 게시도 포함합니다([리비전 복원 계약](profile-spec.md)).

| 재배포 전 상태 | `--activate` 후 기대 결과 |
|---|---|
| 승인 대기 중인 도구, 지침만 변경(승인 규칙 불변) | 기존 카드로 승인하면 같은 호출이 정확히 1회 실행됨. |
| 프로세스 교체 사이에 정적 `cron` 예정 시각 경과 | 해당 구간 리비전으로 1회 실행, 여전히 허용된 도구는 성공, 데드레터 0건. |
| 새 리비전에서 이전 리비전 도구 철회 | 직접 도구 호출은 `denied`, 이전 승인 버튼은 `stale`, 도구 실행 0회. 고정 리비전에 없는 도구는 `unknown_tool` 반환. |
| 전달 카드 발급 후 레지스트리에서 대상 제거 | `claude_route_gone`으로 검증: 회차가 `delivery_unrouted`로 종료, 원 대화 알림 1건, 대상 전송 0건. 이전 버튼 재클릭 시 동일 결과. |
| 프로필 A 유지, 프로필 B 제거(B에 번들 없는 데드레터/미소비 구간 존재) | A 교체와 새 프로세스 합류 성공, B에 대한 번들 복원·모델 호출·도구 실행·승인 소비·전송 0건. |
| 이전 리비전 참조가 여전히 필요한 상태에서 같은 ID로 B 재등록 | 원본 누락 시 게시 전 실패하여 A의 활성 세트 보존, 일치하는 ID + 해시 원본 백필 시 복원 가능. |
| 준비 조회 이후 이전 워커가 구 리비전 실행을 접수하는 도중(구 번들 누락) A 교체 | 게시 전 재확인이 해당 구 리비전을 요구하며 백필 전까지 교체 차단, 구 참조 없는 대조 실행은 성공. |
| 두 프로세스가 같은 새 세트 게시, 준비 후 구 워커가 구 실행을 접수하고 한 프로세스가 먼저 복원·게시 | 두 번째 프로세스가 쓰기 충돌을 감지해 합류 전 해당 구 리비전을 복원하며 실패 시 시작 거부. 게시 후 새로운 구 리비전 접수는 `Stale` 반환. 새 고정 참조가 없으면 재준비 없이 바로 합류. |

**번들 백필과 형식 버전:**
- PostgreSQL에 같은 디렉터리를 두 번 백필해도 번들은 하나만 남습니다. 다른 유효한 디렉터리로는 누락 키를 대체할 수 없으며, 같은 키의 손상된 저장 바이트는 덮어쓰지 않습니다. 백필 자체는 활성 세트, 실행 시도, 대기 카드를 변경하지 않습니다.
- 레거시 `BOTPROFILE1` 번들은 `SKILL.md` 프런트매터와 64 KiB 규칙 도입 후에도 헤더 버전에 따라 그대로 복원됩니다. `SKILL.md` 프런트매터를 파싱하는 새 프로필은 `BOTPROFILE2`를 사용해 같은 활성 세트로의 암묵적 크로스 버전 합류를 방지합니다.

### 리스, 대기, 취소 및 운영자 실행 제어

수명 주기: `ready → leased → succeeded | waiting | retry | dead`.

- **취소:** 대상 하위 트리 행을 부모 우선으로 잠가 커밋된 위임은 취소에 합류시키고 취소 이후 위임은 거부합니다. 실행 중인 작업은 취소 요청을 기록해 다음 외부 이펙트 전에 확인하며, 이미 시작된 이펙트는 끝까지 추적합니다. 취소 커밋 후 현재 소유자가 완료를 시도하면 새 답변·응답 없이 `Cancelled`로 닫고 대기 중인 부모를 깨웁니다(사용량과 잘림은 성공 완료 시에만 기록). 완료가 먼저 커밋되었으면 그 결과와 응답이 유지됩니다. 실행 중 취소 확인은 `Failure::Permanent("cancelled")`를 발생시키며 스토어가 이를 확인해 `Cancelled`로 마감합니다.
- **리스와 에포크:** 클레임은 짧은 트랜잭션(`SKIP LOCKED`, 리스 만료, 증가하는 `generation`)을 사용합니다. 하트비트(행 락 아래 DB 시계로 확인), 완료, 자식 생성, 도구 호출은 외부 호출 동안 DB 락을 잡지 않고 소유자·세대·만료를 검증합니다. 모든 클레임(일반 재개 포함)은 새 `claim_epoch`를 발급하므로 해제된 토큰은 갱신·체크포인트·완료·도구 호출을 수행할 수 없습니다.
- **재시도와 대기:** 일시적 오류는 상한 있는 지수 백오프 + 지터를 사용하고, 영구 오류와 시도 소진은 데드레터 처리합니다. 시도 횟수는 소비된 일시적 실패와 리스 만료에서만 증가하며 정상 완료, 영구 오류, 사용자 취소, 승인 대기, 이펙트 보류에서는 증가하지 않습니다. 승인 요청, 자식 위임, 이펙트 보류는 실행을 `waiting`으로 옮기고 리스를 원자적으로 해제합니다. 판정, 대체(supersede), 만료, 자식 결과, 운영자 판정은 같은 세대로 실행을 깨웁니다. 리스 만료 회수는 `generation`을 증가시키고 이전 승인을 `Superseded`로 표시합니다. 승인은 `(profile, run, generation)` 내 클레임 간 유효하며 소비 시 승인자·도구·인자 다이제스트·만료를 재검증합니다. 승인자 전용 컨텍스트 뷰는 실행 토큰을 노출하지 않습니다.
- **운영자 재개 및 취소:** 일반 루트에 대해 관측한 `state`, `generation`, `claim_epoch`를 제출하면 스토어가 락 아래 이를 검증하고 미해결 하위 트리 보류 여부를 확인합니다. 재개는 데드레터 실행에만 적용되며(논리적 실행·이펙트 키 유지, 시도 횟수 `0`으로 초기화), 취소는 미종료 루트에 하위 트리 취소를 적용합니다. 성공 명령은 전환 + 감사를 원자적으로 커밋합니다. 같은 명령 ID와 입력을 재전송하면 이후 세대가 실패했더라도 이전 성공을 반환하고, 같은 ID에 다른 전제조건은 충돌, 새 ID에 오래된 전제조건은 `stale`을 반환합니다. 인증된 운영자와 고정 사유가 감사되며 미해결 이펙트는 보류 해결 UI에서 처리합니다([관리자 API](admin.md)).
- **체크포인트 및 완료 오류:** `MAX_DOC_BYTES`(1 MiB)를 초과하거나 `Invalid`를 반환하는 단계형 모델 체크포인트는 즉시 `invalid_checkpoint`로 종료합니다(한도 내 이미 커밋된 호출별 영수증은 보존). `Unavailable`은 저장된 계획과 영수증을 재사용하며 `checkpoint_unavailable`로 재시도합니다. 완료 `Invalid`/`Conflict`는 `invalid_result`/`finish_conflict`로 종료하고, `Unavailable`은 `finish_unavailable`로 재시도합니다.

### 워커 종료와 리스 회수

1. `SIGTERM`/`SIGINT` 수신 시 `bot serve`는 새 실행 클레임을 중단하고, 진행 중인 실행이 완료되거나 승인 대기로 전환할 수 있도록 하트비트를 유지한 채 **8초 유예 창**을 줍니다.
2. 유예 후 해당 클레임의 모델/도구 프로세스 종료를 확인하고 세션 토큰을 철회한 뒤 `RunStore::release_for_shutdown`을 호출합니다(기본 **10초 정리 예산**). 종료는 모델 VM 기동도 중단합니다. 사전 점검은 기동을 건너뛰고, 이미 시작 중인 VM은 클라이언트를 먼저 중지한 뒤 컨테이너가 없음이 확인될 때까지 반복 삭제합니다(지연된 create 호출이 `stopped` VM을 남기는 것 방지). 종료를 확인할 수 없으면 리스 만료로 다음 워커에 인계합니다.
3. `release_for_shutdown`은 락 아래 미만료 리스, 세대, `claim_epoch`, 취소 상태를 확인한 뒤 시도 횟수를 소비하지 않고(활성 세트가 변하지 않아도) 실행을 `ready`로 되돌리며, 같은 커밋에서 세대를 1 증가시키고 이전 승인을 대체 처리합니다. 종료된 실행과 다른 소유자는 건드리지 않으며, 결과 불명 `Started` 쓰기는 보류/복구를 따릅니다.
4. `SIGKILL`, 크래시 또는 정리/해제 실패 시 회수 워커는 클레임 트랜잭션 내에서 이전 클레임에 기록된 **호스트 전체 활성 세트**와 현재 활성 세트를 비교합니다. 둘 다 알려져 있고 서로 다르면 시도 횟수를 **0회** 소비하고 새 세트를 기록하며, 같거나 없으면(레거시 행) 1회 소비합니다(마지막 시도에서는 `dead(lease_expired)`). 활성 세트 조회 실패 시 상태를 변경하지 않고 재시도합니다. 취소, 세대 증가, 승인 대체는 동일하게 적용됩니다.
5. **감사 결과 코드:** 정상 종료 해제는 `run.release`(`shutdown`), 시도 소비 없는 활성 세트 교체 회수는 `run.reclaim`(`set_replaced`)을 기록합니다.

## 실행 흐름 예시 — 일정 삭제 도중 워커 장애

브로커는 일정 ID와 인자를 고정하고 승인을 얻어 승인 소비 + 호출 시작 + 감사를 커밋한 뒤 MCP 서버를 실행합니다. 서버가 반환하면 재시작을 가로질러 같은 호출 ID로 호출과 영수증이 원자적으로 완료됩니다.

- **결과 불명 외부 쓰기:** 서버 실행 후 결과 없이 프로세스가 죽으면 실제 전송 여부는 알 수 없습니다. 수신 측이 보장하는 멱등성 키나 영수증 조회로만 복구하며, 만료되었거나 증명되지 않으면 `held` 상태를 유지합니다.
- **다중 쓰기 단계 원장:** 선택적 단계 영수증으로 확정된 단계(예: 파일 업로드)를 보존하면서 불확실한 단계(예: 알림)만 판정합니다. 1개 이상 단계가 확정되었는데 최종 도구 응답이 유실되면 전체 호출이 보류됩니다(같은 단계 키는 이전 영수증을 반환하지만 재시작된 도구가 같은 내용에 다른 단계 이름을 고를 수 있음). 운영자가 이전 도구 종료와 전체 호출에 대한 수신 측 영수증을 확인하면 브로커는 도구를 재실행하지 않고 해당 영수증을 반환합니다([도구 콜백](plugins.md)).
- **게이트웨이 응답과 재개 전제조건:** 응답도 동일한 규칙을 따릅니다. 운영자는 외부 영수증이나 명확한 미실행 증거와 함께 판정을 기록합니다. 현재 인증/승인 아래 같은 호출 ID를 재개하기 전에 호스트는 이전 세대 IPC/이그레스를 닫고 이전 도구 프로세스와 자식 프로세스의 종료 **및** 수신 측 미실행 증명을 모두 확인해야 하며, 호스트 연결 끊김이나 불확실 상태에서는 `held`를 유지합니다.
- **내구성 전제조건:** PG 내구성, 검증된 백업, 지원 기간 이상의 중복 제거 보관 기간이 필요합니다. 페일오버 중 접수 유실 0건을 달성하려면 동기 복제와 구 프라이머리 펜싱이 필요합니다. 백업 복원 중에는 외부 송신을 잠그고 수신 측과 대사하세요. 영수증과 멱등성 키가 모두 없는 수신 측은 자동 완료와 중복 0건을 동시에 보장할 수 없습니다.

## 보류 판정 멱등성

스토어는 모든 보류 발생에 `hold_id`를 부여합니다. 응답·단일 도구·민감 DM은 호출당 1개, 다단계 도구는 미확정 단계당 1개, 모든 단계가 확정되었으나 최종 도구 결과가 불명인 경우 별도의 호출 수준 ID를 부여합니다(호출 수준 판정 대상이 없는 레거시 단계 전용 보류도 여기에 표시).

관리자 UI는 최초 조회 시 선택한 `hold_id`를 제출합니다. 스토어는 대상, 발생 회차, 운영자, 판정, 증거 다이제스트를 검증해 전환 + 감사를 원자적으로 커밋합니다. 이전 `hold_id`에 같은 판정을 재전송하면(예: 재전송 후 새 `hold_id`로 다시 보류된 경우) 두 번째 보류를 건드리지 않고 이미 적용된 결과를 반환합니다. 이전 `hold_id`를 다른 운영자·대상·판정·증거로 재사용하면 충돌을 반환합니다. 민감 DM 판정은 원시 증거와 영수증을 저장하지 않습니다.

## 게이트웨이 인계 계약

- **활성 세트 펜싱:** 활성 세트 리비전은 프로필과 유효 게이트웨이 신원/진입점 매핑을 모두 포함합니다(CLI OS 사용자 하나만 바뀌어도 새 세트 생성). 접수, 승인 판정, 응답 `begin`, 관리자 판정은 활성화 교체와 동일한 DB 락 아래 활성 세트를 검증하므로, 교체가 커밋되면 오래된 진입점은 `Stale`로 실패하고 이미 시작된 전송의 영수증은 계속 수용됩니다.
- **상태 조회:** `(profile, binding, authenticated principal, request)`를 키로 합니다. 현재 진입점으로 동일 입력이 재전달되면 원래 실행을 재사용하며, 신규 접수는 대상 프로필 리비전도 확인합니다.
- **민감 DM과 `private_pass: true`:**
  - 전용 비공개 원장에서 리스를 획득하고 호출 직전 도구·입력 HMAC·리스·활성 리비전을 검증하며, 시작을 1회 기록한 뒤 원시 도구 출력/오류를 폐기하고 완료/통과/거부/보류 상태만 보관합니다. 승인이나 단계 콜백이 필요한 도구는 여기에 연결할 수 없습니다.
  - `private_pass: true`가 허용한 유효한 빈 PASS는 비공개 원장 마감 및 감사와 함께 커밋됩니다. 표준 접수 전 프로세스가 죽으면 변경되지 않은 리비전·트리거·프로필별 다이제스트 시크릿으로 동일 이벤트를 재전달해야 복구됩니다. 이 요소들과 매핑된 인자·본문·첨부파일·이벤트 ID에 대한 프로필별 HMAC이 일치하면 완료된 호출을 재사용해 `<request_id>:pass`로 접수합니다. 레거시 게이트웨이로 롤백하면 새 게이트웨이 복원 후 이벤트 재전달 전까지 접수 전 `passed_v2`를 보류하며, 패스 기록 없는 레거시 완료는 비공개 소비 상태로 남습니다.
  - 시작 전 실패 또는 증명된 미전송 + 종료는 리스를 해제하고 ACK를 보류해 재전달이 새 클레임으로 재개되게 합니다. 완료는 시작과 일치해야 하며, 미확인 전송이나 만료 리스는 재전달 없이도 `Held`가 됩니다. 보류 판정은 원시 영수증이나 메모를 저장하지 않습니다.
- **응답 아웃박스와 전송 범위 격리:**
  - 응답은 별도 전송 세대를 사용합니다(`outbox.claim` → 게시 자격 확인 → `begin` 커밋 → 단일 전송). `begin` 전 만료는 회수하고, `begin` 후 불확실은 보류하며, `settle`이 영수증 + 감사를 커밋합니다. 전송 키 `(profile, run, seq)`는 워커 이펙트 원장을 다시 조회하지 않고도 워커 재시작 전반에 유지됩니다.
  - CLI와 HTTP는 인증된 상태 조회로 전달합니다(풀 아웃박스 행 없음, 라이브 CLI 연결도 동일한 커밋 결과를 읽음). 푸시 접수는 호스트가 선택한 어댑터 ID(`reply_transport`)를 실행에 고정하며(재전달과 위임에 상속), 응답 행은 대상 `transport`를 가집니다. PostgreSQL은 본문을 반환하기 전에 어댑터 `transport`와 선택적 `(profile, binding)`으로 `outbox.claim`을 필터링하며, 해당 어댑터 내에서 DM과 채널 게시 방식을 선택합니다. 같은 `run`의 앞선 `pending`/`sending` 응답은 `transport`와 무관하게 후속 시퀀스를 차단합니다. 게이트웨이는 현재 리비전 아래 바인딩·주체·대상 권한을 검증하고 해당 리비전을 `begin`에 전달합니다(불일치 시 `Stale`).
- **마이그레이션 `0026` (`crates/bot-store/migrations/0026_reply_transport.sql`) 및 빈 `transport` 규칙:**
  - **롤아웃과 잠금:** `bot_runs`와 `bot_outbox`에 컬럼을 추가하고 행을 백필한 뒤 `bot_outbox_pending`을 비동시 방식으로 재구축합니다(`ACCESS EXCLUSIVE` / 쓰기 락 — 운영 규모 복제본에서 벤치마크하고, 레거시 쓰기/클레임 프로세스를 중지해 진행 중 전송을 마친 뒤 마이그레이션하고 새 게이트웨이로 재개하세요).
  - **레거시 백필과 감사 쿼리:** 공식 레거시 Slack 원 대화와 승인된 명시적 대상은 `slack`으로 백필되며, 증명이 부족한 행은 `transport = ''`로 남아 자동 클레임에서 제외됩니다. 남은 행과 영향받는 스케줄은 다음 쿼리로 점검하세요.
    - `SELECT profile, run, seq, state, reason FROM bot_outbox WHERE transport = '' AND state IN ('pending', 'sending', 'held')`
    - `SELECT s.profile, s.id, s.origin_run, s.origin_kind FROM bot_user_schedules s JOIN bot_runs r ON (r.profile, r.id) = (s.profile, s.origin_run) WHERE s.state = 'active' AND s.origin_kind IN ('direct', 'channel') AND r.reply_transport IS NULL`
    커스텀 포크 어댑터는 별도로 백필해야 합니다. 레거시 빈 `transport` 보류(`owner_lost` 등)는 `bot_outbox.transport`를 채우기 전까지 재전송할 수 없으며, `reply_transport`가 null인 실행의 활성 사용자 스케줄은 `bot_runs.reply_transport`를 채우면 다음 스윕부터 다시 실행됩니다.
  - **전송 누락 보호:** 응답이나 스케줄 종료 알림을 발행하는 레거시/미매핑 푸시 실행(`reply_transport IS NULL`)은 완료/종료를 실패시키지 않고 즉시 `bot_holds` + 감사(`outbox.held`)에 `state = 'held'`, `reason = 'missing_transport'`로 응답을 엽니다. `reply_transport IS NULL`인 푸시 원 실행에서 새 사용자 스케줄(`Fire`)을 실행하면 `Invalid`를 반환합니다. `transport = ''`에 대한 `not_executed` 재전송은 `Conflict`를 반환하므로, 미실행 해결 전 `bot_outbox.transport`를 채우거나 `bot_outbox.body`를 확인해 수동 전달한 뒤 처리 완료로 닫으세요.
  - **명시적 대상 범위:** 원 대화에 묶인 스케줄 응답과 종료 알림은 생성 실행의 `transport`를 상속하며, 명시적 대상은 현재 Slack 채널(`slack`)로 고정되어 있습니다.
- **HTTP 응답 모드:** 최초 접수 시 메서드, 경로, 응답 모드를 저장하고 `/_requests/{id}`는 원래 모드로 렌더링합니다. 응답 모드는 재시도 해시에서 제외되며, 저장된 모드가 없는 레거시 HTTP 요청은 `accepted`로 렌더링합니다.
- **응답 페이로드와 카드 규칙:**
  - 응답 본문은 `text`(≤12,000자), `attachments`(≤8개 파일, 디코딩 합계 ≤8 MiB, 각 `{name, type, data}`), `approval`(`nonce`, `title`, `lines` ≤20) 중 1개 이상을 담은 JSON 객체입니다.
  - 푸시 대화(`direct`/`channel`)에서 루트 에이전트 답변의 줄 시작 `<attachment name="attachment.md">...</attachment>` 블록은 같은 커밋 안에서 `text`와 후속 `text/plain` `attachments` 응답으로 분할됩니다(문자/바이트/응답 상한 초과 시 `truncated` 기록).
  - `approval`은 승인 원장과 함께 커밋된 브로커 생성 카드에서만 허용됩니다(`Finish.answers`에서는 거부). 상세 내용이 잘릴 정도로 큰 승인 카드는 발행하지 않고 인증된 승인 상세 화면 링크를 제공합니다. 승인 버튼 클릭 시 `Broker::decide`를 실행한 뒤 원장 상태로 카드를 새로고침합니다(새로고침 실패가 판정을 재실행하지는 않음).
- **전송 실패와 재시도:** `begin` 이후 쓰기 전 연결 실패나 수신 측이 미실행을 보장하는 거부(속도 제한, 캐시된 토큰 회전 중 인증 계층 봇 토큰 거부)는 `NotSent`로 정리합니다. 토큰 거부는 캐시된 토큰을 비워 다음 시도에 자격 증명을 다시 로드하게 합니다(반복 거부는 재시도 상한 적용). 숨겨진 게이트웨이/HTTP 재시도는 비활성화됩니다. 스토어는 일치하는 전송 세대의 `sending` 상태에서만 재시도 예약 + 감사를 커밋하며, 다음 클레임은 같은 `(call, seq)`와 새 세대로 `max(backoff, Retry-After)`만큼 대기한 뒤 소진 시 운영자용 영구 실패로 표시합니다. 요청 쓰기 이후 응답 유실, 타임아웃, 부분 첨부 업로드 실패는 `held`가 됩니다.
- **승인, 철회 및 리비전 펜스:**
  - 클릭 시 조건 변경이 감지되면 현재 호출의 nonce만 `Superseded`로 표시하고 감사 + 깨우기를 한 번에 커밋합니다(재클릭은 아무것도 깨우지 않음). 승인 후 철회와 `start`는 단일 원장에서 직렬화되어 철회가 먼저면 `Revoked`, 소비가 먼저면 철회가 `Conflict`를 반환합니다.
  - 스케줄과 위임 자식은 루트에 기록된 에이전트와 트리거 ID에서 현재 승인자를 해석합니다(서비스 주체를 공유하는 스케줄도 각자의 승인자를 따름). 크론 누락, 주체 변경, 비인간 승인자일 경우 승인 필요 호출을 거부합니다.
  - 브로커는 `StartCall.checked_revision`(활성 프로필 리비전)을 전달하며, 스토어는 프로필 교체와 호출 시작을 직렬화합니다(프로필이 먼저 변경/비활성화되면 승인을 소비하지 않고 `Stale`, 아니면 승인 소비 + 시작 + 감사를 원자적으로 커밋). `Outbox::begin`도 같은 펜스를 강제합니다.
  - `memory.share` 승인은 정규 JSON `{"id": ..., "sha256": ...}`(`sha256` = 미리보기 본문 UTF-8 바이트의 소문자 16진 SHA-256)을 해시합니다. 스토어는 해당 행을 잠그고 소유자와 현재 다이제스트를 검증한 뒤(수정되었으면 승인 미소비 `Conflict`) 소비 + 프로필 공개 + 완료 + 감사를 함께 커밋합니다. 완료된 호출 재전달은 이후 편집본을 재게시하지 않으며, 레거시 ID 전용 대기 승인은 새 카드가 필요합니다.
  - `finish`는 현재 소유자와 세대만 수용합니다. 새 소유자가 이전 세대의 `Started`를 만나면 수신 측 증명 + 이전 러너 종료 확인이 있을 때만 복구합니다(그렇지 않으면 원래 소유자·세대·이펙트 영수증을 유지한 채 `Held`). 운영자 메모만으로는 미실행을 증명할 수 없으며, 결과 차단이 불확실한 쓰기를 거부로 덮어쓸 수 없습니다.
  - 감사 항목은 모든 상태 변경과 같은 커밋에서 단일 호스트 전체 체인에 추가되며 운영자가 순차 검증합니다.

### OpenAI 호환 접수 및 조회

`ApiRuns::accept`는 활성 세트를 검증하고 기존 접수를 확인합니다. 새 키라면 진입점 락을 잡고 재확인한 뒤 프로필 리비전과 활성 실행 용량을 검증하여 접수·실행·감사를 원자적으로 커밋합니다.

- **키:** 바인딩과 모델을 아우르는 `(profile, entrance, authenticated principal, Idempotency-Key)`. 일치하는 키 + 입력 다이제스트 + 모델은 새 슬롯·실행·감사 없이 기존 실행(진행 중 또는 종료)에 붙으며, 입력이나 모델이 다르면 쓰기 없이 `Conflict`를 반환합니다.
- **용량:** 활성 실행은 `ready`, `leased`, `waiting`(승인, 자식, 보류), `retry` 상태의 루트 실행입니다(위임 자식은 루트 슬롯 공유). `(profile, entrance)`별 신규 접수는 `pg_advisory_xact_lock`으로 직렬화해 `max_active_runs`(`1`–`256`)를 강제합니다. 가득 차면 `Capacity`, 리비전이 오래되었으면 `Stale`을 반환합니다(쓰기 없음). 이미 커밋된 재시도는 진입점 락을 기다리지 않고 바로 붙습니다.
- **불확실한 커밋:** 커밋 응답이 유실되면 서버가 키로 재조회하며, 여전히 불명확하면 적용된 멱등성 키와 함께 HTTP 422 `request_outcome_unknown`을 반환해 호출자가 같은 키와 본문으로 재시도하게 합니다. 확정 롤백으로 분류하는 SQLSTATE: 무결성 위반(`23xxx`), `40001`, `40002`, `40P01`.
- **조회:** 4튜플 전체를 일치시켜 고정된 모델·바인딩·에이전트·리비전·입력 다이제스트와 상태를 반환합니다. 상태에는 진행 중(`"Request is still in progress. Query again with the same Idempotency-Key and request."`), 승인 대기(`"Awaiting approval. Query again with the same Idempotency-Key and request."` — 루트나 대기 중인 하위에 실행 가능한 사람 승인이 있고, Slack 카드는 확정된 `posted` 영수증 이후에만), 보류, 승인 차단(`no_approver`, `approver_revoked`, `route_changed`, `approval_dm_unavailable` — 저장된 판정에서만 읽음), 최종 텍스트, 실패, 취소가 있습니다.
- **사용량과 잘림:** 최종 텍스트는 워커 자신의 실행 텍스트이며, 호스트가 자른(>12,000자) 응답은 완료 커밋에 `truncated`를 기록합니다. 토큰 사용량은 첫 클레임이고, 위임 자식이 생성되지 않았으며, 모든 모델 요청이 토큰을 보고한 경우에만 같은 커밋에 저장됩니다(`claude-cli`: 모든 요청이 양수 입력+출력을 보고하고 합계가 CLI 총합과 일치, 직접 API `anthropic-api`/`openai-api`: 모든 턴의 업스트림 응답이 합산 가능한 사용량 보고). 그렇지 않으면 비워 두며 0으로 채우지 않습니다. 직접 API 출력 한도 초과는 부분 텍스트나 잘린 도구 호출 없이 `output_limit`으로 실패하며, `claude-cli` 이어쓰기는 최종 텍스트를 저장하고 호스트가 자른 경우에만 `length`를 보고합니다. JSON은 HTTP 422 `run_failed`를 반환하고, 열린 SSE는 `run_failed` 오류 이벤트로 종료합니다([OpenAI 호환 API](gateway.md#openai-호환-api)).
- **격리:** 표준 웹훅/CLI 접수와 상태 조회는 OpenAI 진입점 접수 행을 읽거나 채택할 수 없으며, `(profile, binding, principal, request_id)`가 충돌해도 새 실행을 만들지 않습니다.

### 완료된 호출 재전달

현재 권한을 확인한 뒤 브로커는 `CallLedger::lookup`으로 완료된 호출을 조회합니다. 일반 도구는 이름 + 정규 인자 해시를 일치시키고, 완료된 `memory.share`는 이름 + 저장된 영수증 메모리 ID를 일치시킵니다(이후 편집/삭제에도 영수증은 유지되며 완료 전 편집은 승인과 공유를 중단함). 최초 결과와 재전달 결과 모두 반환 직전에 `active_revision(attempt)`으로 PG의 활성 프로필 리비전과 현재 클레임을 검증하며, 교체·취소·리스 만료·조회 오류 시 확정 영수증은 원장에 유지한 채 결과 반환을 보류합니다.

## 채팅으로 생성한 스케줄

사용자 스케줄은 정적 프로필 트리거와 별도로 저장됩니다. 호스트는 인증된 사람, 에이전트, 원 바인딩/대화/스레드, 권한 상한, `private` 플래그를 고정합니다(위임과 예약 실행은 서비스 계정이나 승인자 권한으로 절대 격상되지 않음). 매 실행 시 현재 구성원·에이전트·바인딩을 확인해 `ceiling ∩ current permissions`로 접수하며, 정책 변경은 도구 호출과 응답 직전에도 적용됩니다. 명시적 대상은 생성 시 승인(수신자 + 지침)과 전달 시 별도 승인(수신자 + 렌더링된 내용)을 모두 요구합니다. 비공개 메모리 가시성과 승인 라우팅은 원 대화를 따릅니다.

- **커밋과 스윕:** 생성/취소는 호출 완료와 원자적으로 커밋됩니다. 스케줄러는 DB 시계로 일회성과 크론 회차를 평가하여 `(profile, schedule_id, scheduled_utc)` 실행, 커서, 다음 예정 시각을 함께 커밋합니다(취소가 먼저면 새 회차 차단, 접수가 먼저면 추적 유지, 동시 스케줄러는 단일 실행으로 수렴). 지연된 회차는 정적 크론의 DST 및 배치 규칙으로 따라잡습니다. 프로필 재활성화는 사용자 스케줄을 삭제하지 않습니다.
- **제한과 `<quiet>`:** `(profile, owner)`당 활성 스케줄 최대 **32개**, 지침 최대 **8 KiB** UTF-8, 자동 깨우기 깊이 최대 **8**(위임으로 깊이 초기화 불가), 도구 후속 깨우기는 부모 도구 영수증과 원자적으로 커밋됩니다(재전달 시 1회만 생성). `quiet: true` 스케줄이 첨부파일 없이 최종 텍스트가 `<quiet>`와 정확히 일치하며 성공하면 결과를 기록하고 응답을 생략합니다(일반 보고, 승인, 실패, 보류는 정상 경로를 따름).
- **생성 봉인과 재전달:** 생성 카드와 PG는 `ScheduleSpec::seal_create()`가 만드는 정규 JSON(JCS)의 SHA-256을 검증합니다. 여기에는 원시 지침, `quiet`(기본 `false`), 명시적 대상, 저장 정밀도에 맞춘 일회성 UTC 밀리초(예: `.250000001Z` → `.250Z`) 또는 5필드 크론 + 해석된 IANA 시간대(기본값은 고정 프로필 리비전의 시간대)가 포함됩니다. 재전달은 미래 시각 검사보다 완료 영수증을 먼저 확인합니다. 레거시 완료 호출은 권한과 다이제스트가 일치하면 영수증을 반환하고, 레거시 카드가 불일치하는 미완료 호출은 새 승인을 요구합니다.

### 위임 결과와 스케줄 게시

워커와 MCP 릴레이는 `delegation_scopes`를 공유해 두 리비전 모두에서 직계 계보, 요청자 역할, 에이전트 상한을 검증합니다(실행 스코프와의 교집합에 `run`이 포함되어야 함). 스토어는 활성 리비전과 현재 클레임을 검증한 뒤 자식을 생성하고 부모를 `waiting`으로 전환합니다. 자식 완료 반환 시 원래 자식, 지침, 부여된 모든 스코프가 여전히 허용되는지 재확인합니다.

어느 역할이 게시하든 활성 세트, 메모리 시드, 정적 트리거 변경이 함께 커밋됩니다(제거된 프로필의 정적 스케줄은 단일 DB 시각으로 닫히고 이전 구간 커서는 보존). 합류 프로세스는 정적 스케줄을 재작성하지 않습니다.

### 명시적 대상 예약 응답

`ScheduleRoutes::resolve`는 호스트 레지스트리가 검증한 Slack 팀과 채널을 `conversation.id`에 고정해 `team_id/channel_id`와 스레드를 생성 카드부터 전달 아웃박스까지 유지합니다. 실행(스케줄러), 승인 열기/소비(브로커), 전송(게이트웨이)에서 검사하며 누락되거나 재바인딩된 라우트는 새 실행과 초안을 차단합니다. 생성 카드와 전달 카드 모두 카드 생성 트랜잭션 안에서 대상을 해석할 때 사용한 호스트 활성 세트를 검증합니다(교체가 커밋되면 오래된 라우트 카드 생성을 차단).

- **초안 봉인:** 워커는 해석된 대상과 최종 답변을 한 번 동결하며, 생성자는 요청 시점과 현재 시점 모두 `schedule.create`를 보유해야 합니다. 명시적 대상 전송은 항상 소유자 승인이 필요하며(비공개 메모리 오염이 있으면 카드에 표기), 바인딩·대화 유형·수신자 ID·스레드와 전송 순서대로의 모든 답변을 표시합니다. `DeliveryDraft::approval_json()`은 `activation`, `target`(스레드 없으면 `null`), `answers`(`text/plain` 첨부파일만 이름·유형·전체 UTF-8 텍스트로 포함 — 예: `data: "aGk="`는 `text: "hi"`로 렌더링, 읽을 수 없거나 크기 초과 번들은 전체 거부)를 인코딩합니다.
- **승인과 큐 등록:** 카드의 **`Delivery draft`** 줄에 이 전체 JSON이 실리고 `DeliveryDraft::sha256()`이 해당 UTF-8 바이트를 해시합니다. 워커 전용 도구 `schedule.deliver`는 리비전 `builtin-1`과 실행별 호출 ID `schedule-deliver`를 사용합니다. PG는 활성 세트와 저장된 초안 다이제스트를 승인과 대조 검증해 승인 소비, 대상 아웃박스 등록, 실행 완료를 원자적으로 커밋합니다(본문 변경·거부·만료·라우트 변경 시 전송 0건). `DeliveryDraft::queued_receipt()`는 등록 건수를 반환하며(예: `{"queued":2}`, 첨부 포함), 응답 유실 시 최신 클레임이 같은 활성 세트 아래 원래 영수증 바이트를 읽고 실제 전달은 게이트웨이가 별도 추적합니다.

| 큐 등록 전 판정 | 회차 결과 |
|---|---|
| 소비 전 소유자가 거부 또는 철회 | `delivery_rejected`(대상이 사라지거나 레지스트리 조회가 실패해도 기록된 소유자 판정이 우선, 원 대화 알림 0건). |
| 현재 레지스트리가 대상을 거부하거나 바인딩이 다른 팀/채널을 가리킴 | `delivery_unrouted`(대상 전송 0건으로 회차 완료, 원 대화에 1회 게시: `"Scheduled delivery route changed; this reply was not sent."`). |
| 레지스트리 일시 장애 | 같은 회차 재시도(승인과 초안 보존, 전송 0건, 알림 0건). |

미전송 정리는 현재 클레임 또는 승인 카드 + 소유자를 검증하고 같은 트랜잭션에서 소유자 판정을 다시 읽은 뒤 최종 사유 + 영수증을 커밋합니다(재전달은 커밋된 영수증 반환, 큐 등록과의 경합에서는 먼저 커밋된 쪽 유지). 원 대화 알림에는 초안이나 대상을 넣지 않으며, 라우트를 복구해도 이미 정리된 회차는 재전송되지 않고 반복 스케줄은 다음 회차에서 다시 검사합니다.

### 소유자 DM 승인 카드 전달 (Slack)

채널 기원 스케줄은 대상 생성과 렌더링된 응답을 소유자의 1:1 DM으로 승인받습니다. 게이트웨이와 스토어는 같은 Slack 설치에서 카드 게시를 확인한 뒤에만 버튼을 활성화하며, 원 채널/스레드에는 짧은 안내만 남깁니다. 로컬 운영자 토큰에는 Slack 소유자 승인 권한이 없습니다.

1. **준비:** 스토어는 `nonce`, 원시 카드 + 해시, 소유자, 원 프로필/바인딩/설치를 바인딩한 단일 전달 작업을 기록합니다(아직 클릭·판정 불가). DB 트랜잭션 밖에서 게이트웨이는 인증된 요청자 == 지정 승인자 Slack 사용자를 확인하고 해당 설치에서 1:1 DM을 열어 전체 카드를 게시합니다(채널 스레드 `ts`는 DM으로 복사하지 않음).
2. **게시 확인:** Slack이 확인한 DM 채널 + 메시지 `ts`가 영수증이 됩니다. 스토어는 영수증·활성 세트·세대·만료를 재검증한 뒤 카드를 원자적으로 열고 원 채널/스레드에 한 줄 안내를 등록합니다: `"Approval request sent via DM"`(초안, 수신자, 해시, 버튼, 승인 ID 없음). 커밋 응답 유실 시 `nonce`로 재조회합니다.
3. **클릭:** 인증된 Socket Mode 세션(또는 서명 진입점의 요청 서명 + 타임스탬프)을 검증합니다. 브로커는 승인자·인자·현재 정책을 재확인하며, 활성 카드에서 저장된 설치·팀·DM·`ts`·`nonce`·클릭자가 모두 일치하는 클릭만 판정할 수 있습니다(채널 바인딩만 활성이고 일반 DM 접수가 꺼져 있어도 동작해야 함). 복사된 메시지나 영수증 확인 전 클릭은 승인을 소비하지 못합니다.
4. **전달 실패:** DM을 열거나 전체 카드를 게시할 수 없으면 요청을 `approval_dm_unavailable`로 닫고, 게시 도중 연결 끊김이나 재시작(결과 불명) 시 버튼을 비활성 상태로 유지하며 자동 재게시하지 않습니다. 스토어는 실행을 원자적으로 깨우고 결과 + 감사를 1회 커밋합니다(정리 응답 유실 시 기존 커밋을 조회하고 같은 작업 정리를 재시도). 생성 승인은 스케줄을 만들지 않고, 전달 승인은 `{"status":"approval_dm_unavailable"}`로 해당 회차를 미전송 완료합니다(반복 스케줄의 향후 회차는 유지). 둘 다 성공 알림 0건, 대상 전송 0건이며 같은 커밋에서 원 채널/스레드에 고정 문구 한 줄을 게시합니다.
   - 전달 불가 확정: `"Approval request could not be sent via DM; request closed."`
   - 게시 결과 불명: `"Could not confirm approval DM delivery; request closed."`
   어느 쪽도 초안, 수신자, 해시, 승인 ID를 포함하지 않으며 재전달 시에도 1회만 발행됩니다. 불명 사례에서 카드가 실제로 게시되었더라도 클릭으로 판정할 수 없으며 `"This request is already closed."`를 표시합니다.

- **타임아웃과 재시도:** 클레임 후 **90초** 동안 시작되지 않은 작업은 회수되고, `sending` 상태로 **120초** 동안 정리되지 않은 작업은 불명으로 닫힙니다. 확정된 일시적 실패(전송 전 연결 오류, 속도 제한, 봇 토큰 거부)는 `max(Retry-After, 5 s)` 대기 후 **6번째** 클레임도 실패하면 `approval_dm_unavailable`로 닫습니다. 진행 중 카드가 만료·판정·무효화되거나 활성 세트가 교체되면 공개 알림 없이 닫힌 상태를 유지합니다. 시스템 종료는 소유자 판정이 아닌 시스템 거부와 `approval.dm_unavailable` 감사 1건을 기록합니다.
- **시도 펜싱:** `begin`, `settle`, `block`은 잠긴 작업 행의 `(nonce, attempt)`와 일치시켜 오래된 재시도가 활성 전송을 방해하지 못하게 합니다. 정리는 락 아래 시도·상태·마감을 검증하며, 사람 클릭은 여전히 `nonce` + 게시 영수증을 사용합니다(참여하는 모든 게이트웨이가 시도 일치를 강제할 때 적용). 이미 열린 카드와 대상 철회는 그대로 `delivery_rejected` / `delivery_unrouted`를 따르며, DM 확인 후에도 대상 아웃박스 등록을 위해 별도의 유효한 전달 승인이 필요합니다.

### OpenAI 호환 일반 도구 승인

접수 기반 API 루트(및 위임 하위)의 승인은 호스트 활성 세트 락 아래 열립니다. 커밋 시점에도 브로커가 확인한 세트가 여전히 최신이어야 하며, 그렇지 않으면 로컬 카드도 Slack 전달 작업도 생성되지 않고 `Stale`이 반환됩니다(미고정 핸들은 거부). 요청자는 접수로 인증된 주체와 일치해야 하며, Slack DM 카드는 브로커가 제공한 값이 아니라 접수 행에 기록된 전달 설치(`team`)를 필수로 사용합니다.

전달 작업은 원 바인딩, 요청자, 리비전, `team`을 고정합니다(HTTP 기원은 채널 알림을 등록하지 않음). 영수증 `team`이 누락되거나 불일치하면 영수증·판정 대상·승인 대기 상태를 만들지 않고 `route_changed`로 닫습니다(지정된 사용자의 클릭으로도 소비 불가). 게시 전 라우트 변경을 감지한 게이트웨이는 `no_approver`, `approver_revoked`, `route_changed`로 `block`을 호출하며(조회에 그대로 반환), 늦게 도착한 판정은 이미 열린 카드를 닫지 않습니다.

### 사용자 스케줄 종료 사유와 스윕

스케줄러는 첫 페이지에서 스윕 상한 `end`를 동결하고 페이징합니다(`after < pos <= end`). `end`는 행 스냅샷이 아니라 키 상한이므로 `end` 이후 새로 도래한 행은 다음 스윕을 기다리고, 커서와 `end` 사이의 행은 현재 스윕에 나타날 수 있습니다. 손상된 행(파싱 불가 크론 또는 대상 유형)도 페이지 크기에 산입되며 ID, 커서, 다음 확인 시각, 종료 사유와 함께 별도 반환됩니다(`due`는 읽기 전용).

- 손상된 행은 스토어 순서 `(at, profile, id)`에 섞어 개별적으로 닫아(활성 프로필이면 읽은 커서 + 현재 리비전으로 `invalid_timing` 또는 `invalid_destination`, 비활성이면 `profile_inactive`) 뒤쪽의 손상된 행 락이 앞쪽 유효 스케줄을 지연시키지 않게 합니다. 스토어 장애는 절대 손상으로 취급하지 않습니다.
- 각 스케줄은 스윕당 최대 1회만 처리합니다. 다음 예정 시각이 여전히 스윕 안에 드는 반복 스케줄은 다음 스윕을 기다리며, 스윕별 "더 처리할 항목 있음" 플래그가 페이지를 넘어 유지되어 기본 간격을 기다리지 않고 즉시 다음 스윕을 시작합니다. 페이지 도중 스토어 오류가 나면 이미 처리된 ID만 건너뛰고 실패 및 남은 스케줄을 재시도하며, 스윕 완료 시 처리 집합을 비웁니다.
- 종료는 `schedule.close` 감사 1건을 원자적으로 커밋합니다. 오래된 커서는 `Stale`을 반환하고(감사·알림 없음), 같은 종료 재전달은 최초 사유를 보존합니다.

| 사유 | 조건 |
|---|---|
| `profile_inactive` | 스토어가 프로필 비활성 상태를 확인함. |
| `member_revoked` | 소유자가 더 이상 현재 프로필의 구성원이 아님. |
| `binding_revoked` | 원 대화 바인딩이 철회됨. |
| `agent_revoked` | 대상 에이전트가 제거됨. |
| `permission_revoked` | `ceiling ∩ current permissions`에 더 이상 `run`이 없음. |
| `invalid_timing` | 저장된 크론 표현식이나 시간대를 파싱할 수 없음. |
| `invalid_destination` | 저장된 명시적 대상 유형을 파싱할 수 없음(원 대화 알림 없음). |
| `finished` | 추가 예정 회차가 없음(마지막 회차 실행 접수와 같은 커밋에서 종료). |
| `unrouted` | 명시적 대상이 호스트 레지스트리에서 사라졌거나 다른 대상으로 매핑됨. |

`unrouted`만 원 대화에 알림을 게시합니다: `"Scheduled message destination is no longer registered; schedule stopped."` 종료, 감사, 단일 알림이 함께 커밋되며(경합하는 스케줄러와 유실 응답 전반에서 중복 제거), 일시적 레지스트리 장애 시에는 커서를 유지하고 재시도합니다.
